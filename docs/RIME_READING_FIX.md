# 0.22.1：读音权重、简拼排序与词典升级

0.22.0 真正的键盘输入中，点 `e` 后首候选为“我”。0.22.1 同样的键盘操作首候选为“额”，前后截图均已目视核对；没有把空输入框、系统切回 Gboard 后的误点或中间版本截图记为最终通过。

## 修复内容

原转换把同一字的所有读音赋成同一个词频。固定 Luna 源文件中，“我”的 `e`/`wo` 权重是 0%/100%，“给”的 `gei`/`ji` 是 99.99%/0.01%，“的”的 `de`/`di` 是 99.97%/0.03%。现在用 Decimal 保留百分比或明确的数值；未声明的读音使用 Essay 词频或默认 100，简体合并后的同字同码取最大值，避免重复放大。

首字母简拼及 zh/ch/sh 简拼改用固定源 `pinyin.yaml` 的 `abbrev` 规则。原来的 `derive` 把简拼当成普通完整读音，使 en/er 词挤到 e 前面。修复后保留简拼能力；`nh` 能完整选“你好”，不强行把所有有歧义的简拼固定为某一个首选。固定原文见 [Luna Pinyin 模块](https://github.com/rime/rime-luna-pinyin/blob/46acf03142c12b5aeed7002675046bf7255eed35/pinyin.yaml)。

Rime 数据从固定 Luna/Essay 和固定 OpenCC 转换程序独立重建，未合并旧 Vime 拼音数据。编译表从 25816412 字节降至 14804388 字节，实际 ARM64 测试 APK 从 25546351 降至 21072656 字节。它是去掉错误读音扩张、重建公共数据后的结果；不是总体输入正确率或所有场景的性能结论。

## 升级与恢复

公共词典按 `dataset_id`放入独立目录。先检查固定文件集合、数据标识和每个文件的 SHA-256，后台流式校验与原子写入；原生引擎成功初始化后再发布活动标识并清理旧公共目录。数据版本变化时清理的 `user/build`是生成缓存，根用户词典、SQLite 生词/复习和设置保留。旧目录清理失败不会把已可用的输入法改成失败状态。

本次在专用 API36/16KB 模拟器上，以正式保存的 0.22.0 测试 APK 作为升级起点。旧版通过自己的存储接口保存两个词，再从真实复习界面答对一次。最终 0.22.0→0.22.1 覆盖升级后，全部 SQLite 行的规范哈希、各项设置及两个已有原生用户词库 SST 文件保持一致；私有保留标记仍在，旧生成缓存和旧公共目录已清理。未卸载应用，未在实体手机造数或安装。

另将一个已部署的公共 table 文件损坏为 6 字节。下一次正常启动从 APK 自动修复到期望 SHA-256，之后再次检查学习行、设置和既有 SST 文件仍相同。此检查没有损坏用户数据库，也不等于已提供严重学习库损坏的一键修复。

## 实际验证

- 15 项词库生成器检查通过，包含原始比例、简体重复合并、多音字释义、来源引用及异常输入拒绝。
- 两次独立生成的 12 个明文文件相同；两次隔离原生编译的 7 个输出逐字节一致。
- 每轮 34 组完整输入/九键均命中预期首候选；另验证 `nh`完整候选、4 个罕见读音反例及 `e`完整读音优先。没有用简拼的歧义排名冒充全拼排名。
- 最终 APK 的 8 项真实 JNI 检查通过，包含全长“真的假的”、九键切换、分页、重复切换、实际学习及新目录的内存映射；兼容回退关闭，进程确实使用 16KB 页，结束后恢复属性。
- 在上述升级与恢复检查后，另通过 14 项输入数据检查，覆盖新目录下的显式重置、重新初始化、并发、公开词典保留和收藏/复习快照恢复。这组检查主动清除了模拟器的选词习惯，升级时保留的旧 SST 随显式清理删除。
- JVM 共 116 项，115 通过、1 项原有可选词包数据集检查跳过；静态资源/隐私检查 44 项通过；debug lint 为 0 错误、167 警告。
- 用 0.22.0 的真实接口执行 16 项隔离存储检查与造数，再经 UI 产生非空复习记录，作为上述升级基线；这不是额外宣称 0.22.1 全部存储流程已重新验收。
- 三个实际 APK 检查了版本、同一预览证书、权限、原生 ELF/ZIP 对齐、包体和打包许可内容。debug 预览在严格生产检查中的 `not_debuggable`、`https_only_network_config`和 `not_preview_certificate`仍失败，完整原始报告保留；其他检查通过。它们没有被记为生产包通过。
